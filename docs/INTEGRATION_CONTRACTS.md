# Взаимодействие Bitrix24, 1С и SyncGuard

Проверенная цепочка v0.2: HTTP-симулятор Bitrix24 → REST-адаптер → нормализованные сделки → Python rule engine ← нормализованные заказы ← OData-адаптер ← HTTP-симулятор 1С. SyncGuard читает данные и фиксирует нарушения; он не выполняет обмен заказами между внешними системами.

## Bitrix24

Адаптер выполняет POST `crm.item.list`, `entityTypeId=2`, сортировку `id ASC`, выбирает нужные поля и проходит страницы по `next`. POST здесь вызывает метод чтения. Финальный `total` должен совпасть с числом уникальных объектов. Успех сделки определяется `stageSemanticId=S`, в том числе для пользовательских воронок; `movedTime` задаёт начало SLA. `updatedTime` не заменяет событие смены стадии. Поля суммы/валюты/контакта: `opportunity`, `currencyId`, `contactId`.

Контракт основан на официальных документах: [crm.item.list](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-list.html), [поля CRM-объекта](https://apidocs.bitrix24.com/api-reference/crm/universal/object-fields.html). Устаревающий `crm.deal.list` не используется.

Текущая модель требует contactId; сделки только с companyId нуждаются в отдельном согласованном преобразовании клиента. Коды валют должны быть трёхбуквенными. Сделка без достоверного времени WON даёт UNKNOWN.

## 1С

Адаптер читает OData JSON, по умолчанию коллекцию `Document_CustomerOrder`. Имена объектов и полей зависят от конфигурации и публикации базы. Публикация OData — поддерживаемый механизм [интеграции 1С](https://1c-dn.com/blog/methods-of-integration-with-1c-enterprise-applications/), но приведённые ниже имена являются контрактом нашего стенда, а не обещанием одинаковой схемы всех баз.

| Нормализованное значение | Поле стенда | Требование для реальной базы |
|---|---|---|
| external_id | Ref_Key | Стабильный уникальный ID заказа |
| created_at | Date | Фактическое время создания, не редактируемая дата документа |
| updated_at | UpdatedAt | Достоверное время изменения |
| amount | Total | Денежная сумма без потери точности |
| currency | Currency | Код валюты, не GUID справочника |
| customer_id | Customer | Согласованный ID клиента, не произвольное представление |
| external_reference | CRMDealID | Внешний ID соответствующей сделки Bitrix24 |

`field_map` конструктора OneCConnector сопоставляет эти ключи с полями публикации. Для валют/контрагентов, представленных ссылками на справочники, нужна дополнительная нормализация до этого контракта. Настройка `timezone_name` задаёт пояс дат без смещения; timezone-aware значения сохраняют свой offset. Значение по умолчанию UTC подходит только стенду. Проверка не должна считать документную Date фактическим временем создания без подтверждения владельца базы.

Поддерживаются `odata.count` / `@odata.count`, `odata.nextLink` / `@odata.nextLink`. Если nextLink отсутствует, а count больше уже прочитанного, используется `$skip`. Серверная пагинация описана в [OData server-driven paging](https://oasis-tcs.github.io/odata/one-pager/server-driven-paging.html). nextLink может содержать токен, но должен оставаться на том же origin и точном пути коллекции. Изменение пути или redirect отклоняются. Count обязателен для доказательства завершённого чтения. Публикации с другим форматом, неподдерживаемыми полями или семантикой времени дадут UNKNOWN до адаптации.

## Защита от неполных и неверных результатов

- Ошибки сети, 429 и 5xx: до трёх попыток чтения; числовой Retry-After учитывается в пределах бюджета. HTTP-date Retry-After пока не поддерживается.
- 401/403, redirect, неверный JSON, error payload, несогласованное count, повтор external_id и выход nextLink за коллекцию: ошибка коннектора.
- По умолчанию 20 секунд на коллекцию, до 100 страниц, до 10 000 объектов, до 2 MB декодированного тела на ответ, до 5 секунд ожидания сетевой операции. Стриминг проверяет общий бюджет при получении каждого блока; это не гарантия жёсткого wall-clock прерывания зависшего синхронного драйвера.
- Суммы декодируются в Decimal. Некорректные ID, неоднозначные даты и дробные суммы вне принятой точности отклоняются; автоматическое округление не выполняется.
- Неуспешный сбор → UNKNOWN, без создания missing_target на основании недоступности. Ранее активные инциденты и риск сохраняются.
- Пагинация не обеспечивает распределённую транзакцию между двумя системами. Изменения данных во время чтения могут потребовать повторной проверки; одинаковое count само по себе не доказывает неизменность содержимого.

## Что фактически проверено

`tools/verify_stack.py` отправляет запросы в запущенный frontend/nginx → FastAPI → HTTP-симуляторы и проверяет данные, записанные в PostgreSQL. 11 запусков проверяют baseline, дедупликацию, восстановление, reopen, отказ 1С, дубли, суммы, задержку, pending и возврат к baseline. JSON-отчёт: [acceptance-http.json](acceptance-http.json). Pytest дополнительно проверяет ошибки протокола и транзакции.

Доступа к реальным тестовым установкам не было. Для приёмки на них нужны URL публикаций, предоставленные через безопасную серверную конфигурацию учётные данные с правом чтения, карта полей/справочников, часовой пояс и несколько контролируемых сделок/заказов. Demo API не принимает эти параметры. Он всегда использует синтетический стенд; подключение реальных tenants ещё требует отдельного onboarding/configuration слоя.
